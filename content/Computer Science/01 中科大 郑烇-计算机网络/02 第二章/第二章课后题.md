### 1.1.2	R17 问题解答

#### 1.1.2.1	1\. "How many `Received:` header lines are there?" (有多少条 `Received:` 头?)

在上面的示例邮件头中，总共有 **4** 条 `Received:` 头。

#### 1.1.2.3	📬 邮件路径分析 (从下往上)

**`Received:` Header \#4 (最底部 - 邮件的起点)**

```
Received: from [192.168.1.10] (alice-desktop.local)
      by mail-server.example-sender.com (Postfix 3.5.8) with ESMTP id 8B7C123456
      for <bob@gmail.com>;

```

  * **分析：** 这是邮件的第一跳。

  * `by mail-server.example-sender.com`: 邮件被 Alice 公司的**外发邮件服务器**（`example-sender.com`）接收。
  * `with ESMTP`: 使用的是标准 SMTP 协议。
  * `Mon, 27 Oct 2025 17:00:01 +0000 (UTC)`: UTC 时间 17:00:01，邮件离开 Alice 的电脑。

-----

**`Received:` Header \#3 (第二跳 - 跨越互联网)**

```
Received: from mail-server.example-sender.com (mail-server.example-sender.com. [198.51.100.5])
        by mx.google.com with ESMTPS id 6si1234567abc.71.2025.10.27.10.00.03
        for <bob@gmail.com>
        (version=TLS1_3 cipher=TLS_AES_256_GCM_SHA384);
        Mon, 27 Oct 2025 10:00:03 -0700 (PDT)

  * **分析：** Alice 的服务器将邮件发送给 Bob 的邮件服务商（谷歌）。
  * `from mail-server.example-sender.com [198.51.100.5]`: Alice 公司的服务器（现在显示其**公网IP**）正在发送。
  * `by mx.google.com`: 邮件被**谷歌的邮件交换 (MX) 服务器**接收。
  * `with ESMTPS`: 使用了**安全的、加密的** SMTP (注意那个 "S")。括号里显示它使用了 `TLS1_3` 加密。
  * `Mon, 27 Oct 2025 10:00:03 -0700 (PDT)`: 谷歌在太平洋时间 10:00:03 收到邮件（注意时区变化，`17:00 UTC` 确实等于 `10:00 PDT`）。

**`Received:` Header \#2 (第三跳 - 谷歌内部路由)**

```

```

  * **分析：** 邮件在谷歌的数据中心内部被传递。
  * `by 10.10.10.11`: 谷歌的**内部服务器**（`10.10.10.11` 是一个内部IP）接收了邮件。这可能是用于垃圾邮件扫描或分发。
  * 这比上一跳晚了 1 秒钟 (`10:00:03` -\> `10:00:04`)。

-----

**`Received:` Header \#1 (最顶部 - 最后一跳)**

```
Received: by 2002:a05:620a:1111:b0:44a:1234:5678 with SMTP id a1csp1234567abc;

  * `by 2002:a05:...`: 另一台谷歌**内部服务器**（一个 IPv6 地址）处理了该邮件。
  * `Mon, 27 Oct 2025 10:00:05 -0700 (PDT)`: 邮件在 10:00:05 被最终处理。

## 1.2	P7 计算查询时间

假设您在 Web 浏览器中点击一个链接来获取一个网页。该 URL 对应的 IP 地址没有在您的本地主机中缓存，因此需要进行 DNS 查询来获取 IP 地址。假设在您的主机从 DNS 收到 IP 地址之前，总共访问了 $n$ 个 DNS 服务器；连续访问这些服务器产生的 RTT (往返时间) 分别为 $RTT_1, \dots, RTT_n$。

此外，假设与该链接关联的网页只包含一个对象，即大量的 HTML 文本。设 $RTT_0$ 为本地主机与包含该对象的服务器之间的 RTT。假设该对象的传输持续时间为 $0.002 \times RTT_0$，那么从客户端点击链接到客户端接收到该对象总共需要多少时间？

总时间是从点击链接开始，到接收完整个对象为止所经过的所有步骤的总和。

1.  **DNS 查询时间:**
    * 客户端需要依次访问 $n$ 个 DNS 服务器。
    * 总 DNS 时间 = $RTT_1 + RTT_2 + \dots + RTT_n$。

2.  **TCP 连接建立时间:**
    * 获取 IP 地址后，客户端需要与 Web 服务器建立 TCP 连接（三次握手）。
    * 这需要 1 个 $RTT_0$。

3.  **HTTP 请求和对象传输时间:**
    * 建立连接后，客户端发送 HTTP 请求。服务器收到请求后发回对象。
    * 请求和接收到对象的**第一个字节**需要 1 个 $RTT_0$。
    * 问题中提到，该对象是“大量的 HTML 文本”，其**传输持续时间**为 $0.002 \times RTT_0$。这部分时间是在收到第一个字节后，接收剩余全部内容所需的时间。
    * 因此，此步骤总时间为 $RTT_0 + 0.002 \times RTT_0$。

**总时间：**
将所有步骤的时间相加：
$$\text{总时间} = (RTT_1 + RTT_2 + \dots + RTT_n) + RTT_0 \text{ (TCP 建立)} + (RTT_0 + 0.002 \times RTT_0) \text{ (请求与传输)}$$
$$\text{总时间} = 2.002 \times RTT_0 + RTT_1 + RTT_2 + \dots + RTT_n$$


## 1.3	P8

再次考虑问题 P7，并假设 $RTT_0 = RTT_1 = RTT_2 = \dots = RTT_n = RTT$。此外，假设有一个新的 HTML 文件，该文件小到传输时间可以忽略不计，它引用了同一服务器上的**九个**同样很小的对象（传输时间也忽略不计）。

在以下情况下，总共需要多少时间？

a) 非持久性 HTTP，没有并行的 TCP 连接？
b) 非持久性 HTTP，浏览器配置了 6 个并行连接？
c) 持久性 HTTP？


---

首先，我们根据 P8 的假设简化 RTT：
* $RTT_0 = RTT_1 = \dots = RTT_n = RTT$

**所有情况的共同步骤：**

在浏览器获取任何对象之前，必须先完成两件事：
1.  **DNS 查询:**
    * 时间 = $RTT_1 + \dots + RTT_n = n \times RTT$。
2.  **获取基础 HTML 文件:**
    * 这个 HTML 文件本身也是一个对象（尽管很小）。
    * 建立 TCP 连接: $1 \times RTT_0 = 1 \times RTT$。
    * 请求和接收 HTML 文件: $1 \times RTT_0 = 1 \times RTT$。
    * 获取 HTML 时间 = $2 \times RTT$。

**"启动"总时间（获取 HTML 文件）= $(n \times RTT) + (2 \times RTT) = (n+2)RTT$。**

在 $(n+2)RTT$ 时间后，浏览器解析了 HTML，发现还需要下载 **9 个** 嵌入的对象。接下来的时间取决于 HTTP 的模式：

**a) 非持久性 HTTP，无并行**

* **非持久性：** 每个对象都需要一个全新的 TCP 连接。
* **无并行：** 必须一个接一个地串行下载。
* 下载 1 个小对象的时间 = $1 \times RTT$ (建立 TCP) + $1 \times RTT$ (请求/接收) = $2 \times RTT$。
* 下载 9 个对象的时间 = $9 \times (2 \times RTT) = 18 \times RTT$。

**总时间 (a) = 启动时间 + 9 个对象的时间**
$$\text{总时间} = (n+2)RTT + 18 \times RTT = (n + 20)RTT$$



**b) 非持久性 HTTP，6 个并行连接**

* **非持久性：** 每个对象都需要一个新 TCP 连接。
* **6 个并行：** 浏览器可以同时打开 6 个连接。
* 启动时间仍然是 $(n+2)RTT$。
* 下载 9 个对象：
    * **第 1 轮：** 并行下载对象 1-6。这 6 个下载同时开始，每个都需要 $2 \times RTT$。此轮耗时 $\max(2RTT, \dots, 2RTT) = 2 \times RTT$。
    * **第 2 轮：** 下载剩余的 3 个对象 (对象 7-9)。此轮耗时 $\max(2RTT, 2RTT, 2RTT) = 2 \times RTT$。
* 下载 9 个对象的总时间 = $2 \times RTT$ (第一轮) + $2 \times RTT$ (第二轮) = $4 \times RTT$。

**总时间 (b) = 启动时间 + 9 个对象的时间**
$$\text{总时间} = (n+2)RTT + 4 \times RTT = (n + 6)RTT$$

**c) 持久性 HTTP**

* **持久性：** 浏览器重用为获取基础 HTML 而建立的 TCP 连接。
* 启动时间仍然是 $(n+2)RTT$。此时，TCP 连接仍然打开。
* 我们分两种标准情况讨论（这也对应您图片中的 `c)` 部分）：

**c.1) 持久性，无流水线 (Pipelining)**
* 浏览器在开放的连接上发送 1 个请求，等待响应完成后，再发送下 1 个请求。
* 下载 1 个小对象的时间 = $1 \times RTT$ (请求/接收)。(不再需要 TCP 建立时间)
* 下载 9 个对象的时间 = $9 \times (1 \times RTT) = 9 \times RTT$。

**总时间 (c.1) = 启动时间 + 9 个对象的时间**
$$\text{总时间} = (n+2)RTT + 9 \times RTT = (n + 11)RTT$$

**c.2) 持久性，有流水线 (Pipelining)**
* 浏览器在开放的连接上，连续发送所有 9 个请求，而无需等待响应。
* 服务器也连续发回 9 个响应。
* 下载 9 个对象的时间：
    * 客户端发送完所有请求（时间忽略不计）。
    * 第一个请求的响应在 $1 \times RTT$ 后到达。
    * 由于所有对象都很小（传输时间忽略不计），所有 9 个响应会紧随其后相继到达。
    * 接收完所有 9 个对象总共只需要 $1 \times RTT$。

**总时间 (c.2) = 启动时间 + 9 个对象的时间**
$$\text{总时间} = (n+2)RTT + 1 \times RTT = (n + 3)RTT$$

---

### 1.3.1	总结

* **P7 答案:** $2.002 \times RTT_0 + RTT_1 + \dots + RTT_n$
* **P8 (a) 答案:** $(n + 20)RTT$
* **P8 (b) 答案:** $(n + 6)RTT$
* **P8 (c) 答案:**
    * 无流水线: $(n + 11)RTT$
    * 有流水线: $(n + 3)RTT$

## 1.4	P9: Web 缓存性能分析

### 1.4.1	问题描述

考虑一个场景：机构网络通过一个路由器连接到互联网，接入链路带宽为 $R = 15 \text{ Mbps}$。假设机构内部用户平均每秒请求 $\alpha = 16$ 个对象，每个对象平均大小为 $L = 850 \text{ kbits}$。从机构路由器到源服务器的平均往返时间 (RTT) 为 3 秒（这包括了传输和处理延迟）。

a.  计算总的平均响应时间（从请求发出到对象接收完毕）。需要计算流量强度 $I = \alpha L / R$ 和接入链路上的平均排队和传输延迟 $t_{access} = (L/R) / (1-I)$。
b.  现在机构安装了一个 Web 缓存，假设命中率 $hit = 0.4$。计算总的平均响应时间。假设访问缓存的延迟（查找时间等）为 $t' = 10 \text{ ms}$。![[attachments/bea07205a3402d9b5aba496051bc9daa_MD5.png]]

### 1.4.2	a. 无缓存情况

**计算:**

1.  **传输时间 ($t_{\Delta}$):**
    $t_{\Delta} = L/R = (850 \times 1000) / (15 \times 10^6) \approx 0.0567 \text{ s}$ (教师计算为 0.05675 s)
2.  **流量强度 (I):**
    $I = \alpha \times L / R = 16 \times (850 \times 1000) / (15 \times 10^6) \approx 0.907$
3.  **接入延迟 ($t_{access}$):** (包括排队延迟和传输延迟)
    $t_{access} = t_{\Delta} / (1 - I) \approx 0.05675 / (1 - 0.907) = 0.05675 / 0.093 \approx 0.61 \text{ s}$ (教师计算为 0.575 s)【这是前面推过的公式】
4.  **总平均响应时间 (t):**
    $t = (\text{局域网延迟}) + (\text{接入延迟}) + (\text{互联网及服务器延迟})$
    假设局域网内部延迟 $t_{LAN} \approx 10 \text{ ms} = 0.01 \text{ s}$ (教师似乎使用了这个值)。
    互联网及服务器延迟 $RTT_{origin} = 3 \text{ s}$。
    $t = t_{LAN} + t_{access} + RTT_{origin} \approx 0.01 + 0.575 + 3 = 3.585 \text{ s}$ (教师计算为 3.575 s)

**结果:** 无缓存时，平均响应时间约为 3.575 秒。

### 1.4.3	b. 有缓存情况 (命中率 0.4)

**计算:**

1.  **未命中率 (Miss Rate):** $1 - hit = 1 - 0.4 = 0.6$
2.  **接入链路上的新流量强度 ($I'$):** 只有未命中的请求会通过接入链路。
    $I' = \alpha \times (1 - hit) \times L / R = 16 \times 0.6 \times (850 \times 1000) / (15 \times 10^6) = 0.6 \times I \approx 0.6 \times 0.907 \approx 0.544$
3.  **接入延迟 ($t'_{access}$):** (只针对未命中的请求)
    $t'_{access} = t_{\Delta} / (1 - I') \approx 0.05675 / (1 - 0.544) = 0.05675 / 0.456 \approx 0.124 \text{ s}$
4.  **命中时的响应时间 ($t_{hit}$):**
    $t_{hit} = (\text{局域网延迟}) + (\text{缓存访问延迟})$
    $t_{hit} \approx t_{LAN} + t' = 10 \text{ ms} + 10 \text{ ms} = 20 \text{ ms} = 0.02 \text{ s}$ (假设教师的 $t'=10ms$ 是缓存查找时间)
    *教师在计算中似乎只用了 10ms，可能代表从局域网用户到缓存的总时间*
5.  **未命中时的响应时间 ($t_{miss}$):**
    $t_{miss} = (\text{局域网延迟}) + (\text{缓存访问延迟}) + (\text{接入延迟}) + (\text{互联网及服务器延迟})$
    $t_{miss} \approx t_{LAN} + t' + t'_{access} + RTT_{origin} \approx 0.01 + 0.01 + 0.124 + 3 = 3.144 \text{ s}$
    *如果按教师计算方法只计一次 10ms: $t_{miss} \approx 0.01 + 0.124 + 3 = 3.134 \text{ s}$*
6.  **总平均响应时间 (t):**
    $t = (hit \times t_{hit}) + ((1 - hit) \times t_{miss})$
    使用教师的方法: $t \approx (0.4 \times 0.01) + (0.6 \times 3.134) = 0.004 + 1.8804 = 1.8844 \text{ s}$
    (教师计算结果为 1.874 s)

**结果:** 加入缓存后，平均响应时间显著降低到约 1.88 秒。

**原因:**
* 40% 的请求在本地缓存快速响应，避免了通过慢速接入链路和互联网。
* 由于 40% 的流量被缓存拦截，接入链路的流量强度从 0.907 下降到 0.544，大大减少了排队延迟 ($t_{access}$ 从 0.575s 降到 0.124s)。

## 1.5	P10: HTTP 传输时间计算

### 1.5.1	问题描述

考虑一条带宽 $R = 150 \text{ bps}$ 的链路，远端服务器通过该链路发送数据。分组（包括数据分组和控制分组如握手、请求）的双向往返时间（RTT）假定为固定值（虽然题目未给出具体值，但在计算中会考虑）。

假设每个 HTTP GET 请求都获得一个 HTML 文件（基础对象），大小为 $L = 100 \text{ kbit}$。该基础对象包含 10 个指向其他对象的引用（例如图片），每个被引用的对象大小也是 $L = 100 \text{ kbit}$。

控制分组（如 TCP 连接建立、HTTP 请求）的大小为 $L' = 200 \text{ bit}$。

假设有 N 个并行连接时，每个连接获得 $1/N$ 的链路带宽。

**问题:**

a.  使用非持续 HTTP 和 10 个并行 TCP 连接下载所有对象（基础对象 + 10 个引用对象）需要多长时间？
b.  使用持续 HTTP（无流水线）下载所有对象需要多长时间？
c.  比较这两种情况下的并行 HTTP 的并发开销是否有意义？现在考虑持续 HTTP，你认为它的性能有很大增益吗？评价并解释你的答案。

### 1.5.2	a. 非持续 HTTP，10 个并行连接

**分析:**

1.  **下载基础对象:**
    * 需要建立一个 TCP 连接（1 RTT，传输 SYN (L')，SYN-ACK (L')，ACK (L')）。
    * 发送 HTTP 请求（1 RTT，传输 GET (L')）。
    * 服务器传输 HTML 文件（传输 L）。
    * 如果忽略 RTT 中的传输时间，每次对象获取需要 2 RTT 的往返延迟，加上控制分组和数据分组的传输时间。
    * 教师简化计算（似乎侧重传输时间或使用了特定模型）：认为获取一个对象需要 3 次控制分组传输 ($3 \times L'/R$) 和 1 次数据分组传输 ($L/R$)。总时间 $T_{obj} = 3(L'/R) + L/R$。此外还需加上往返传播延迟。
    * 初始基础对象下载时间 $t_{initial} = 3 \times (200 / 150) + (100 \times 10^3 / 150)$ 秒。（注意：这里 k=1000）
    * $t_{initial} \approx 3 \times 1.33 + 666.67 = 4 + 666.67 = 670.67$ 秒。

2.  **下载 10 个引用对象 (并行):**
    * 基础对象下载完成后，浏览器同时发起 10 个 TCP 连接请求。
    * 每个连接过程与下载基础对象类似，但带宽被 10 个连接共享 ($R/10 = 15 \text{ bps}$)。
    * 获取一个引用对象的时间（并行时单个连接花费的时间） $t_{parallel\_single} = 3 \times (L' / (R/10)) + (L / (R/10))$。
    * $t_{parallel\_single} = 3 \times (200 / 15) + (100 \times 10^3 / 15)$ 秒。
    * $t_{parallel\_single} \approx 3 \times 13.33 + 6666.67 = 40 + 6666.67 = 6706.67$ 秒。
    * 由于 10 个连接并行进行，这部分的总时间取决于最慢的那个连接完成的时间，即 $t_{parallel} = t_{parallel\_single}$。

3.  **总时间:**
    * $T_{total} = t_{initial} + t_{parallel} \approx 670.67 + 6706.67 = 7377.34$ 秒。
    * 教师计算结果为 7377 秒。

## 1.7	P22: C/S 与 P2P 文件分发时间

### 1.7.1	问题描述

考虑向 N 个对等方分发一个大小为 F = 15 Gbits 的文件。服务器具有上传速率 $u_s = 30 \text{ Mbps}$。每个对等方（客户端）具有下载速率 $d_i = 2 \text{ Mbps}$ 和上传速率 $u_i$。考虑三种情况的 $u_i$: 300 kbps, 700 kbps, 2 Mbps。

计算 N = 10, 100, 1000 时，对于每种 $u_i$ 组合，客户端-服务器 (C/S) 模式和对等网络 (P2P) 模式下的最小分发时间。用表格形式给出结果。

(假设 $d_{min} = 2 \text{ Mbps}$)

### 1.7.2	客户端-服务器 (C/S) 模式

**分析:**
在 C/S 模式下，文件分发时间由两个因素决定：
1.  服务器将 N 份文件副本全部上传完毕所需的时间。
2.  下载速度最慢的客户端下载完一份文件副本所需的时间。
最小分发时间是这两者中的较大值。客户端的上传速率 $u_i$ 在此模式下不起作用。

**公式:**
$D_{C/S} = \max \{ \frac{NF}{u_s}, \frac{F}{d_{min}} \}$

**计算:**

$F \approx 15 \times 1024 \text{ Mbits} = 15360 \text{ Mbits}$
$u_s = 30 \text{ Mbps}$
$d_{min} = 2 \text{ Mbps}$

* **N = 10:**
    * $NF/u_s = 10 \times 15360 / 30 = 5120 \text{ s}$
    * $F/d_{min} = 15360 / 2 = 7680 \text{ s}$
    * $D_{C/S} = \max(5120, 7680) = 7680 \text{ s}$
* **N = 100:**
    * $NF/u_s = 100 \times 15360 / 30 = 51200 \text{ s}$
    * $F/d_{min} = 7680 \text{ s}$
    * $D_{C/S} = \max(51200, 7680) = 51200 \text{ s}$
* **N = 1000:**
    * $NF/u_s = 1000 \times 15360 / 30 = 512000 \text{ s}$
    * $F/d_{min} = 7680 \text{ s}$
    * $D_{C/S} = \max(512000, 7680) = 512000 \text{ s}$

* **瓶颈:** 在 C/S 模式下，当 N 较大时，服务器上传带宽 $u_s$ 成为瓶颈。在 P2P 模式下，瓶颈可能是服务器上传第一个副本 ($F/u_s$)，最慢客户端下载 ($F/d_{min}$)，或者是总上传能力 ($NF/(u_s + \sum u_i)$)。当 N 很大且客户端上传能力 $u_i$ 较高时，瓶颈往往是最慢客户端的下载速度 $F/d_{min}$。
* **效果:** P2P 利用了对等方的上传能力，大大减轻了服务器的负担，尤其在分发大文件给大量用户时，效率远高于 C/S 模式。

## 1.8	P23: C/S 文件分发方案设计

### 1.8.1	问题描述

考虑使用客户端-服务器（C/S）体系结构向 N 个用户分发 F 比特的文件。假定服务器上传速率为 $u_s$，每个用户的下载速率为 $d_i$，$d_{min}$ 是所有用户中的最小下载速率。服务器不能同时向多个用户流式传输，组合速率不能超过 $u_s$。

a.  假设 $u_s / N \le d_{min}$。定义一个分发方案。
b.  假设 $u_s / N \ge d_{min}$。定义一个分发方案。
c.  得出最小分发时间通常是 $\max \{ NF/u_s, F/d_{min} \}$ 所决定的结论。

### 1.8.2	分析与方案

**基本模型:**
* 服务器 S，上传速率 $u_s$。
* N 个客户端 $P_1, P_2, ..., P_N$。
* 客户端 $P_i$ 的下载速率为 $d_i$。
* $d_{min} = \min \{ d_i \}$。
* 文件大小 F。
* 目标：将文件 F 分发给所有 N 个客户端。
* 最小分发时间 $t = \max \{ NF/u_s, F/d_{min} \}$ (这是已知的 C/S 模式下的理论最小时间)。

**a. $u_s / N \le d_{min}$ (服务器相对较慢或客户端很多)**

* **条件解读:** 这个条件意味着，如果服务器平均地将它的上传带宽分配给所有 N 个客户端，那么每个客户端得到的带宽 $u_s/N$ 不超过（小于等于）最慢客户端的下载能力 $d_{min}$。换句话说，$u_s \le N \times d_{min}$。服务器的总上传能力不足以同时满足所有客户端以 $d_{min}$ 的速度下载。服务器的上传是瓶颈。
* **分发方案:** 服务器以其最大能力 $u_s$ 进行上传。它可以将这 $u_s$ 的带宽同时分配给 N 个客户端，每个客户端获得 $u_s/N$ 的速率。由于 $u_s/N \le d_{min} \le d_i$ (对所有 i)，每个客户端的下载速率被服务器的分配所限制，实际下载速率为 $u_s/N$。
* **时间分析:**
    * 服务器需要上传的总数据量是 $N \times F$。它以 $u_s$ 的总速率上传，所需时间为 $NF/u_s$。
    * 每个客户端需要下载 F 比特的数据。它以 $u_s/N$ 的速率下载，所需时间为 $F / (u_s/N) = NF/u_s$。
    * 由于 $u_s/N \le d_{min}$, $NF/u_s \ge F/d_{min}$。因此 $\max \{ NF/u_s, F/d_{min} \} = NF/u_s$。
    * 此方案下，所有客户端同时开始下载，并同时在 $NF/u_s$ 时间后完成。这符合最小分发时间 $t = NF/u_s$。
* **方案总结:** 服务器同时向所有 N 个客户端传输文件，每个连接分配 $u_s/N$ 的带宽。

**b. $u_s / N \ge d_{min}$ (服务器相对较快或客户端较少)**

* **条件解读:** 这个条件意味着，如果服务器平均分配带宽，每个客户端得到的 $u_s/N$ 将超过最慢客户端的下载能力 $d_{min}$。换句话说，$u_s \ge N \times d_{min}$。服务器有足够的能力同时以 $d_{min}$ 的速度服务所有客户端，甚至可能更快。此时，最慢客户端的下载能力 $d_{min}$ 可能是瓶颈。
* **分发方案:** 服务器仍然可以尝试同时服务所有 N 个客户端。对于客户端 $P_i$，服务器可以提供的最大速率是 $u_s/N$（如果平均分配），但客户端 $P_i$ 只能以 $d_i$ 的速率接收。因此，客户端 $P_i$ 的实际下载速率是 $\min(u_s/N, d_i)$。
    * 由于 $u_s/N \ge d_{min}$，对于最慢的客户端，其实际下载速率是 $\min(u_s/N, d_{min}) = d_{min}$。
    * 对于其他客户端 $P_i (d_i > d_{min})$，其实际下载速率是 $\min(u_s/N, d_i)$，这个值 $\ge d_{min}$。
* **时间分析:**
    * 服务器需要上传的总数据量为 $N \times F$。它实际使用的总上传带宽是多少？是 $\sum_{i=1}^{N} \min(u_s/N, d_i)$。这个值 $\le N \times (u_s/N) = u_s$。服务器上传完所有数据所需的时间是 $NF / (\sum \min(u_s/N, d_i))$。
    * 最慢的客户端下载需要的时间是 $F / d_{min}$。
    * 其他客户端下载需要的时间是 $F / \min(u_s/N, d_i) \le F/d_{min}$。
    * 因此，整个分发完成的时间取决于最慢的客户端完成下载，或者服务器完成所有上传。
    * 由于 $u_s/N \ge d_{min}$, $NF/u_s \le F/d_{min}$。因此 $\max \{ NF/u_s, F/d_{min} \} = F/d_{min}$。
    * 在此方案下，最慢的客户端在 $F/d_{min}$ 时刻完成。服务器是否在此之前完成了所有上传？服务器需要的总时间 $T_{server} = NF / (\sum \min(u_s/N, d_i))$。因为 $\min(u_s/N, d_i) \ge d_{min}$，所以 $\sum \min(u_s/N, d_i) \ge N d_{min}$。因此 $T_{server} \le NF / (N d_{min}) = F/d_{min}$。所以服务器总能在最慢客户端完成之前或同时完成上传。
    * 此方案下，总时间由最慢客户端决定，为 $F/d_{min}$。这符合最小分发时间 $t = F/d_{min}$。
* **方案总结:** 服务器同时向所有 N 个客户端传输文件。每个客户端 $P_i$ 以 $\min(u_s/N, d_i)$ 的速率下载。

**c. 结论**

无论在哪种情况下 ($u_s/N \le d_{min}$ 或 $u_s/N \ge d_{min}$)，通过上述的分发方案，达到的分发时间分别是 $NF/u_s$ 和 $F/d_{min}$。

结合两种情况：
* 当 $u_s/N \le d_{min}$ 时， $NF/u_s \ge F/d_{min}$，此时最小时间为 $NF/u_s = \max \{ NF/u_s, F/d_{min} \}$。
* 当 $u_s/N \ge d_{min}$ 时， $NF/u_s \le F/d_{min}$，此时最小时间为 $F/d_{min} = \max \{ NF/u_s, F/d_{min} \}$。

因此，在客户端-服务器模式下，无论服务器和客户端的具体速率关系如何，能够达到的最小分发时间总是由服务器总上传瓶颈 ($NF/u_s$) 和最慢客户端下载瓶颈 ($F/d_{min}$) 中的较大者决定，即：
$t_{min} = D_{C/S} = \max \{ \frac{NF}{u_s}, \frac{F}{d_{min}} \}$


## 1.9	P2P 文件分发系统时间分析 (P24)

本节课主要分析 P24 题目，探讨 P2P (Peer-to-Peer) 文件分发系统所需的最短时间，并与 P23 的 C/S (Client-Server) 模型进行对比。

### 1.9.1	P2P 分发时间下限公式

在 P2P 文件分发系统中，假设有一个服务器和 N 个客户端（Peer），需要将一个大小为 F 的文件分发给所有 N 个客户端。

最小分发时间 $D_{P2P}$ 满足以下不等式：

$$
D_{P2P} \ge \max\left\{\frac{F}{u_s}, \frac{F}{d_{min}}, \frac{NF}{u_s + \sum_{i=1}^{N} u_i}\right\}
$$

首先，老师在 01:03 处回顾了 P2P 分发时间的三个下限（瓶颈）：
1.  **服务器上传瓶颈：** $D \ge F/u_s$ （服务器至少要传出一个完整文件）
2.  **最慢下载瓶颈：** $D \ge F/d_{min}$ （下载最慢的客户端也需要下载完）
3.  **系统总上传瓶颈：** $D \ge NF / (u_s + \sum u_i)$ （N个客户端总共需要 $NF$ 的数据量，系统总上传能力为 $u_s + \sum u_i$）

本题P24假设 $d_{min}$ 非常大，所以我们**忽略第2个瓶颈**。因此，最小分发时间 $D_{min} = \max\{F/u_s, NF/(u_s + \sum u_i)\}$。


### 📚 a 问的策略

这种情况可以等价地写为 $Nu_s \le u_s + U$，即 $(N-1)u_s \le U$ 或 $u_s \le \frac{U}{N-1}$。这意味着服务器的上载带宽 $u_s$ 相对于平均每个客户端能提供的上载带宽 $U/(N-1)$ 来说较小。![[attachments/b4ea5d22f91990de60c3ba0435c9ddea_MD5.png]]

**条件：** $u_s \le (u_s + u_1 + \dots + u_N)/N$
* 这个条件可以转换为 $N u_s \le u_s + \sum u_i$，即 $(N-1)u_s \le \sum u_i$。
* 老师在 18:40 左右的讲解中指出，这个条件意味着 $F/u_s \ge NF / (u_s + \sum u_i)$。
* **结论：** 在此条件下，**服务器的上传速率 $u_s$ 是系统的瓶颈**。

**目标：** 设计一个分发方案，使其时间恰好为 $F/u_s$。

**策略（基于老师 06:50 - 13:20 的讲解）：**
该策略的核心是让服务器始终保持 $u_s$ 的满速率上传，并且利用对等方（Peers）的高上传能力（由 $(N-1)u_s \le \sum u_i$ 保证）来相互分发。

1.  **服务器（S）**：在 $D = F/u_s$ 的全部时间内，以 $u_s$ 的速率持续上传文件内容。服务器将其带宽 $u_s$ 分配给 $N$ 个对等方，例如按比例 $r_i$ 分配给 $P_i$，使得 $\sum r_i = u_s$。
2.  **对等方（Peers）**：
    * 每个对等方 $P_i$ 一旦从服务器或其他对等方收到了文件的任何部分，就**立即**以其最大上传速率 $u_i$ 将这些部分上传给其他 $N-1$ 个对等方。
    * 由于 $d_{min}$ 远大于 $u_s$ 和 $u_i$，对等方的下载带宽不是瓶颈。
3.  **结果：** 由于对等方的总上传能力 $U = \sum u_i$ 足够大（ $U \ge (N-1)u_s$ ），它们有能力在 $F/u_s$ 时间内，将从服务器收到的数据（总共 $F$）以及它们彼此之间的数据（总共 $U \times (F/u_s)$）进行充分交换，确保所有 $N$ 个节点都能下载完 $F$。系统的瓶颈在于服务器将第一份完整文件 $F$ 注入系统的速度。

**简而言之：** 服务器以 $u_s$ 全速上传，所有对等方以 $u_i$ 全速“接力”上传。因为对等方“接力”的能力足够强（满足条件a），所以总时间取决于服务器这个“源头”的速度。

---

### 📚 b 问的策略

**条件：** $u_s \ge (u_s + u_1 + \dots + u_N)/N$
* 这个条件可以转换为 $(N-1)u_s \ge \sum u_i$。
* 老师在 21:20 左右的讲解中指出，这个条件意味着 $F/u_s \le NF / (u_s + \sum u_i)$。
* **结论：** 在此条件下，服务器相对“快”，而**系统的总上传能力 $u_s + \sum u_i$ 是瓶颈**。

**目标：** 设计一个分发方案，使其时间恰好为 $D = NF / (u_s + \sum u_i)$。

**策略（基于老师 21:20 - 27:50 的精巧设计）：**
该策略的核心是让**服务器和所有 $N$ 个对等方**在整个分发期间 $D$ 内，**同时**以各自的最大上传速率（$u_s$ 和 $u_i$）满负荷工作。

1.  **文件划分（流体模型）：** 老师在 21:30 处将文件 $F$ 划分为 $N+1$ 个逻辑流（streams）。
2.  **服务器（S）的上传策略（总速率 $u_s$）：**
    * 对于 $i=1 \dots N$，服务器以 $r_i = u_i / (N-1)$ 的速率向对等方 $P_i$ 发送“**流 $i$**”。
    * 服务器使用其剩余的带宽 $r_{N+1} = u_s - \sum_{i=1}^N r_i = u_s - (\sum u_i) / (N-1)$，向**所有 $N$ 个**对等方广播“**流 $N+1$**”（即每个对等方收到 $r_{N+1}/N$ 的速率）。
    * （*检查：* $u_s \ge (\sum u_i)/(N-1)$，这个条件在b中成立，所以 $r_{N+1} \ge 0$）。
3.  **对等方（Peers）的上传策略：**
    * 每个对等方 $P_i$ 在收到服务器发来的“**流 $i$**”后，立即以其最大速率 $u_i$ 将“**流 $i$**”转发给所有其他 $N-1$ 个对等方（即向每个其他对等方以 $u_i / (N-1)$ 的速率发送）。
4.  **结果（验证）：**
    * **服务器满载：** 总上传速率为 $\sum_{i=1}^N r_i + r_{N+1} = u_s$。
    * **对等方 $P_i$ 满载：** 总上传速率为 $(N-1) \times [u_i / (N-1)] = u_i$。
    * **对等方 $P_k$ 的总下载速率 $d_k$：**
        * 来自服务器的“流 $k$”：$r_k = u_k / (N-1)$
        * 来自服务器的“流 $N+1$”：$r_{N+1} / N = (u_s - (\sum u_i) / (N-1)) / N$
        * 来自其他 $N-1$ 个对等方的“流 $i$” ($i \ne k$)：$\sum_{i \ne k} [u_i / (N-1)]$
    * 将三者相加（如老师在 27:10 处的推导），$d_k = (u_s + \sum u_i) / N$。
    * 由于每个对等方都以这个速率接收，下载完 $F$ 的时间 $D = F / d_k = NF / (u_s + \sum u_i)$。该策略恰好达到了瓶颈时间。

---

### 📚 c 问的策略

这是一个**结论性问题**，策略是基于a和b的分析进行总结。

1.  P2P分发的最小时间 $D_{min}$ 必须大于等于所有瓶颈中的最大值。在忽略 $d_{min}$ 的情况下，$D_{min} \ge \max\{F/u_s, NF/(u_s + \sum u_i)\}$。
2.  **在情况a中**（$u_s$ 是瓶颈），我们找到了一个策略，使得 $D = F/u_s$。
3.  **在情况b中**（$u_s + \sum u_i$ 是瓶颈），我们也找到了一个策略，使得 $D = NF / (u_s + \sum u_i)$。
4.  **结论：** 由于在任一情况下（$u_s$ 是瓶颈或 $u_s + \sum u_i$ 是瓶颈），我们都能设计出一个方案来达到该瓶颈对应的下限时间。因此，在一般情况下，最小分发时间就是这两个瓶颈中的**较大值**。
5.  **所以， $D_{min} = \max\{F/u_s, NF/(u_s + u_1 + \dots + u_N)\}$**。

## 1.10	P25 Overly Network的相关问题

考虑一个**覆盖网络** (overlay network)，该网络有 $N$ 个活动的对等方 (peer)，**每对**对等方之间都有一个活动的 TCP 连接。此外，假设这些 TCP 连接总共通过了 $M$ 个路由器。

在相应的覆盖网络中，有多少个**节点** (node) 和**边** (edge)？


这道题的关键在于理解“覆盖网络”(Overlay Network) 的定义。

* **覆盖网络**是一个构建在另一个网络（称为底层网络，underlay network）之上的逻辑网络。
* 在覆盖网络中，**节点 (Nodes)** 是指网络中的端系统或对等方 (peers)。
* 在覆盖网络中，**边 (Edges)** 是指节点之间建立的**逻辑连接**（例如 TCP 连接），无论它们在底层物理网络中走了多远或经过了多少路由器。

### 1.10.1	1. 节点 (Nodes) 的数量

* 根据定义，覆盖网络的节点就是它的 $N$ 个活动的对等方 (peers)。
* 因此，**节点的数量 = $N$**。
* 题目中提到的 $M$ 个路由器是底层物理网络的组件，**不是**覆盖网络的节点。

### 1.10.2	2. 边 (Edges) 的数量

* 题目说明“**每对**对等方之间都有一个活动的 TCP 连接”。
* 这描述了一个**全连接**（fully connected）的图，其中 $N$ 个节点中的每一个都与其他所有节点相连。
* 我们可以使用组合数学来计算：从 $N$ 个节点中任意选取 2 个节点组成一条边，总共有多少种组合？
* 边的数量 = $C(N, 2) = \frac{N \times (N-1)}{2}$

**举例验证：**
* 如果 $N=3$ (节点 A, B, C)，边有 3 条 (A-B, A-C, B-C)。公式： $3 \times (3-1) / 2 = 3$。
* 如果 $N=4$ (节点 A, B, C, D)，边有 6 条 (A-B, A-C, A-D, B-C, B-D, C-D)。公式： $4 \times (4-1) / 2 = 6$。

### 1.10.3	答案

* **节点数量: $N$**
* **边的数量: $\frac{N(N-1)}{2}$**

(注：$M$ 个路由器的信息是用来迷惑的，它们属于底层网络，与覆盖网络的拓扑结构无关。)
